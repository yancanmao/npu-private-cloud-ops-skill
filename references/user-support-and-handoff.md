# 用户支持与管理员接手

## 职责路由

| 请求 | 执行身份和入口 |
| --- | --- |
| 组件解释、如何使用面板、登录、SSH | 普通用户上下文；平台仓库 `skills/coder-platform-user` |
| 本人工作区/已有应用操作 | 当前用户的 Coder UI/CLI；操作授权与资源范围由用户请求确定 |
| 调度事件、卷故障、模板缺项、网关/发现异常 | 本 ops skill，使用已经获授权的运维上下文；不从用户会话提权 |
| 平台安装、发布、存储/回收策略、多平台同步 | 读 deployment / storage-and-acceptance，走既有计划与完整验收 |

组件百科的共同来源是平台仓库的 services、模板和前端清单，不在多个 skill 内各自维护真实
地址、端口、面板数值或凭据。基础概念见
[平台用户指南](https://github.com/yancanmao/npu-private-cloud/blob/main/skills/coder-platform-user/references/platform-guide.md)。
管理员定位手册保留已有部署、恢复、安全和报告要求，不把普通用户所有问题都变成集群故障。

## 接手时的最小信息

先读用户已有报告：目标平台、本人账号标识和工作区 ID、模板/build、观察时间（含时区）、
症状、可见短错误、已做检查、未确认假设、当前任务和保护范围。用户已提供的信息不再问。
缺什么只补什么；不要求普通用户交出密码/token、宿主机密钥、admin 账号或 kubeconfig。
发起求助或发送给其他聊天/管理员需要用户明确授权，本 skill 不自动发送。

普通用户 403 只证明其检查受权限限制，不能当成平台故障；管理员用自己的已授权身份读取
目标对象事件。账号、工作区 owner、实际执行者是不同字段，尤其共享 admin 账号下不能只
看名字就认定归属。发现错误登录平台/身份先修正上下文，不直接启停对象。

## 分层证据

- Connecting：Coder build → Pod 分配/启动/挂载 → Agent 回连 → 用户终端；按失败点检查。
- 有空卡但不能启动：逐节点整份 CPU/内存/NPU 申请 → 队列/节点/拓扑 → 存储与镜像事件。
- No data：应用是否存在 → metrics 导出 → 当前对象登记 → scrape → 时间/筛选/查询。
- 写满：容器路径 → 实际挂载 → 宿主机文件系统 → 额度/实际占用/临时峰值；节点镜像盘
  与 Longhorn 卷池分别核算，不把容器 /root、宿主机 /root 和 /data 混成同一对象。
- 模板更新后应用消失：原 build/app/sidecar/socket/持久目录与仓库声明对照；先保留数据与
  工作负载，不以复制别人的工作区或重建用户卷代替可复现修复。

面板矛盾、未替换的链接占位符、旧工作区缺按钮都作为不同缺陷记录，不能为了顺便修好
而扩大线上变更。已授权的平台发布仍须覆盖两端全部前端与可视化；用户只读教学不是一次发布。

## 接手与交付边界

用 diagnostic-report 的六段结构回答用户原始问题。说明哪些是用户可以执行的操作，哪些
必须由管理员处理；提供可复核依据。临时恢复、预检阻止重试、真正修复和最终验收分别记录。
用户任务尚未完成时不能以管理员测试 PASS 结项；提交补丁也不自动等于修题正确或性能有收益。
源码/skill 同步与生产功能同步分别报告，不能因为安装了两个 skill 就宣称平台已一致。
